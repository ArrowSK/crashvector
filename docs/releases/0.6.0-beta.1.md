# CrashVector 0.6.0-beta.1

M14 extends the current Godot rigid-body production path to vulnerable road-user targets and removes the visibly rigid behaviour of narrow pole/tree targets at severe collision demand. It also contains a focused desktop-UI correction for the evidence-scope modal reported during packaged-beta testing.

## What changed

- Pedestrian targets now run through a real `RoadUserRigidProxy3D` / Godot `RigidBody3D` world-motion path instead of being blocked or silently falling back to the historical reduced-order pair solver.
- Riderless bicycle targets use the same rigid-body contact/trajectory architecture.
- The existing pedestrian and bicycle structural objects remain presentation/contact proxies inside the rigid body. They are not biomechanical, injury or rider models.
- Passenger-car world motion remains on the stable M12/M13 `RigidBody3D` chassis path. The front probe transfers a reduced-mass contact impulse to a vulnerable target while the existing phenomenological nose-crush resistance remains on the car side.
- Generic pole and tree targets now begin as anchored/frozen rigid fixtures and can release into permanent motion when generic collision demand exceeds their yielding capacity. Wall and concrete barrier remain rigid.
- Replay and production metrics retain the road-user rigid-body trajectory state without changing the M13 passenger-car whole-body failure architecture.

## Evidence-scope UI correction

The Calibration / evidence-scope modal retained its original CanvasLayer while the M10 desktop shell moved to a higher layer. The panel could therefore appear underneath the current UI, leaving the visible **Close** button unable to receive input.

M14 makes the smallest possible correction: the existing calibration/evidence CanvasLayer is placed immediately above the current M10 desktop CanvasLayer. The panel content, ownership and callbacks are unchanged.

A production regression now opens the evidence-scope control used by labels such as **Extrapolated**, verifies that the normal CrashVector UI remains present, verifies that the modal is above the desktop UI, closes it through its existing Close control, and verifies that the normal UI remains intact afterwards.

## Regression and packaging gates

M14 adds engine-physics and production-routing coverage for:

- passenger car versus stationary adult pedestrian proxy with material post-contact target trajectory;
- passenger car versus stationary riderless city-bicycle proxy with material post-contact target trajectory;
- severe generic pole and tree impacts producing substantial permanent target motion;
- wall and concrete barrier remaining non-yielding under the new obstacle API;
- bounded passenger-car vertical/rebound behaviour in the new scenarios;
- pedestrian/bicycle production routing through `RoadUserRigidProxy3D` rather than the historical direct `Pedestrian` / `Bicycle` world-motion path;
- the evidence-scope modal open/close regression described above.

The historical road-user editor smoke test was updated only where it still expected the pre-M14 direct `Pedestrian` / `Bicycle` node. Application physics was not changed to satisfy that stale assertion.

M10, M11, M12, M13 and M14 dedicated validation, canonical Core CI, macOS Universal 2 packaging and the Windows x64 installer lifecycle remain release gates for the final M14 head.

## Modelling scope

CrashVector remains an educational visualisation tool. Pedestrian output is contact/trajectory visualisation only: it does not calculate injury, survivability, HIC, AIS, tissue loading or dummy-equivalent metrics. The bicycle target is riderless.

Pole/tree yielding thresholds and moving masses are phenomenological generic project parameters. They are not claims about a particular lamp post, utility pole, tree species, trunk diameter, soil condition or foundation design.

Rigid lorry and motorcycle production simulation remain blocked pending their own rigid-body ports. Visual Compare and Comparison Lab remain unavailable pending a scene-based rigid-body comparison recorder. CrashVector does not silently substitute the historical reduced-order world solver for those production results.
